# План пользовательского тестирования Memento

Ветка: `feat/memento-standup-integration`  
База: актуальный `main`, включая ранее влитые PR #13, #15 и #17  
Цель: проверить одним прогоном уже влитые функции и весь открытый стендап-стек, не смешивая ошибки сборки, распознавания, суммаризации и продуктового UX.

## Единая ветка для тестирования

Для пользовательского и командного тестирования используйте только:

- ветку `feat/memento-standup-integration`;
- draft PR #37;
- зафиксированный commit из шаблона обратной связи.

Отдельные feature PR образуют stacked-историю разработки и нужны для точечного
review. Их не нужно последовательно переключать, собирать или устанавливать.

Для нового клона:

```bash
git clone git@github.com:andyzt/meet_at_giga.git
cd meet_at_giga
git fetch origin
git switch --track origin/feat/memento-standup-integration
cd frontend
pnpm install
pnpm run tauri:dev
```

Для существующего клона:

```bash
git fetch origin
git switch feat/memento-standup-integration
git pull --ff-only
cd frontend
pnpm install
pnpm run tauri:dev
```

Не удаляйте пользовательские данные и не используйте `git reset --hard` для
обновления тестовой копии. Если рабочее дерево изменено, сохраните изменения или
создайте отдельный чистый клон.

Эта ветка является тестовой, а не production-релизом. Управляемые DeepSeek и
SaluteSpeech используют `gw.multitool.works` с резервом
`gw2.multitool.works`; облачные сценарии проверяются только после явного
согласия пользователя. Локальные режимы можно тестировать без отправки
транскриптов во внешний сервис.

## Что вошло в сборку

### Уже было в `main`

- рабочее пространство коллекций и навигация по сериям встреч (PR #13);
- усиленная индексация и RAG, обязательные ссылки на источники и защита от ответа без доказательств (PR #15);
- выбор движка распознавания, SaluteSpeech, чувствительность тихих/Bluetooth-микрофонов и build key (PR #17);
- локальный gateway bootstrap (PR #18);
- исправленный bootstrap чистой сборки (PR #19).

### Добавлено поверх `main`

- явная миграция старых управляемых LLM-настроек без скрытой отправки данных;
- надёжная суммаризация DeepSeek с соблюдением выбранной модели, ограниченными повторами и без неявной подмены провайдера;
- приватное автоопределение встречи по процессам и активности микрофона;
- массовый импорт папки: SHA-256 dedupe, возобновление, отмена и отчёт;
- Standup V2: структурированные апдейты, блокеры, решения и задачи с доказательствами из расшифровки;
- проверка каждого извлечённого факта: принять, исправить, отклонить, переоткрыть задачу или отметить выполненной;
- pre-brief, перенос незакрытых задач, дайджест серии и локальная лента проактивных инсайтов;
- личные заметки до встречи, parking lot, ручной таймбокс и маркеры живого стендапа;
- объяснимое предложение стендап-шаблона вместо автоматического переключения;
- безопасные кандидаты имён спикеров с доказательствами, подтверждением, алиасами и фильтрацией оскорблений;
- выбор основного интервала встречи при длинной паузе и поздних фрагментах;
- исправление `token_type_ids` для локальных ONNX-эмбеддингов;
- приватный corpus runner и eval-инструменты для повторяемого сравнения качества;
- исправление конкурентной работы self-hosted reviewer workflow.

## Важные ограничения теста

- Не используйте DeepSeek без явного согласия на отправку текста и действующих credentials. Если он недоступен, тест должен завершиться понятной ошибкой, а не переключиться на другую модель.
- Локальный Qwen baseline пока не является эталонным качеством. Оценивайте точность фактов и удобство review-потока, а не только красоту текста.
- Имена из разговора всегда должны оставаться кандидатами. Приложение не должно автоматически переименовывать или объединять людей.
- Личные заметки и live-маркеры не являются доказательствами из транскрипта и не должны попадать в модель как будто их произнёс участник.
- Не фиксируйте реальные расшифровки, имена или приватные eval-отчёты в GitHub issues/PR. Для обратной связи достаточно ID встречи, времени фрагмента и обезличенного описания.

## 0. Подготовка и smoke build

1. Переключиться на `feat/memento-standup-integration` и убедиться, что рабочее дерево чистое.
2. Проверить свободное место: желательно не менее 25 ГБ для полной Tauri-сборки и моделей.
3. В `frontend` выполнить `pnpm install`, затем `pnpm run tauri:dev`.
4. Если нужна именно production-проверка, отдельно выполнить `pnpm run tauri:build`.
5. На первом запуске убедиться, что база открылась, старые встречи видны, настройки не сброшены, DevTools не показывает бесконечных циклов ошибок.

Критерий: приложение запускается, список встреч открывается, запись можно начать и остановить, существующие данные сохранены.

## 1. Регрессия записи и распознавания

Провести короткую встречу на 3-5 минут с микрофоном и системным аудио.

- Пауза и продолжение не создают вторую встречу и не теряют аудио.
- В транскрипте нет очевидного удвоения микрофона и системного звука.
- Переключение между доступными ASR-провайдерами применяется к следующей записи.
- Режим повышенной чувствительности захватывает тихую речь; при обычном микрофоне не создаёт поток ложных сегментов.
- После остановки доступны редактирование транскрипта, переход по времени и экспорт.

Зафиксировать: выбранные устройства, ASR-провайдер/модель, длительность, пропущенные фразы и ложные фрагменты.

## 2. Автоопределение встречи

1. Включить автоопределение в настройках.
2. Открыть нативное приложение для звонка и проверить одно уведомление о начале записи.
3. Повторить для браузерного звонка в Chrome/Arc/Opera: одного микрофонного сигнала без вкладки звонка недостаточно для частых ложных уведомлений.
4. Не отвечать на уведомление, свернуть приложение, затем вернуть его из tray.
5. Отключить функцию и повторить сценарий.

Критерий: детектор ничего не записывает сам, не сохраняет список процессов, объединяет повторные сигналы и полностью замолкает после отключения.

## 3. Массовый импорт

Использовать небольшую тестовую папку: два разных аудиофайла и копию одного из них.

1. Запустить импорт папки и отменить его в середине.
2. Запустить ту же папку повторно.
3. Проверить, что готовые файлы пропущены по хэшу, незавершённые продолжены, а копия не создала дубль.
4. Проверить JSON-отчёт: imported/skipped/failed, исходный путь, хэш и причина пропуска согласованы с базой.
5. Проверить непустые транскрипты и открытие импортированных встреч.

Критерий: отмена отличается от ошибки, повторный запуск идемпотентен, metadata сохраняется до признания импорта готовым.

## 4. Обычное саммари и провайдеры

На одной и той же встрече создать саммари локальной моделью и, только при согласии, DeepSeek.

- Выбранная в конкретном диалоге DeepSeek-модель действительно используется.
- Русский текст генерируется напрямую, без отдельного перевода и смешения языков.
- Ошибка credentials, timeout или исчерпание повторов видны пользователю.
- Нет тихого fallback на Ollama, другой cloud provider или другую модель.
- Повторная генерация не оставляет старый структурированный результат под новым markdown.

Оценить по шкале 1-5: фактическая точность, полнота решений/задач, лишние утверждения, читаемость, время до результата.

## 5. Content window

Использовать запись, где после основной встречи есть длинная тишина и несколько поздних реплик.

1. Убедиться, что приложение предлагает основной интервал и показывает границы.
2. Сначала выбрать полную расшифровку, затем основной интервал и пересоздать саммари.
3. Изменить границы/состав поздних фрагментов и проверить повторный запрос согласия.

Критерий: аудио и транскрипт не удаляются; выбор влияет только на будущий вход суммаризации; старое согласие не применяется к новым границам.

## 6. Standup V2 на реальном стендапе

Выбрать минимум три стендапа из разных серий: чистый status round, стендап с deep dive и запись с неполным началом/концом.

- Предложение шаблона объясняет причину и требует подтверждения.
- Для каждого участника корректно разделены сделано, план, блокер, решение и action item.
- Владелец и срок отсутствуют, если они не названы явно.
- Каждая запись с доказательством открывает правильный момент транскрипта.
- Две реплики в одну секунду не подтверждают цитату неоднозначно.
- Неполный ответ помечается как неполный, а не дополняется выдуманными фактами.
- Форматирование markdown не ломает синхронизацию структурированных данных.

Для каждой ошибки записать: категория, обезличенный ожидаемый факт, фактический результат, timestamp доказательства, серьёзность.

## 7. Review и жизненный цикл задач

1. Принять правильный факт.
2. Исправить текст, владельца или срок и сохранить с подтверждением.
3. Отклонить ложный факт и затем вернуть его на проверку.
4. Отметить action item выполненным и переоткрыть.
5. Перезапустить приложение.

Критерий: состояния сохраняются; отклонённое не становится фактом серии; элементы с одинаковым текстом, но разными владельцами не склеиваются.

## 8. Серия, pre-brief, дайджест и инсайты

Добавить несколько стендапов в одну коллекцию и подтвердить часть записей.

- Pre-brief показывает только подтверждённые открытые задачи, недавние блокеры и решения.
- Перенос задачи не создаёт дубли и сохраняет историю статусов.
- Дайджест привязан к датам встреч, а не к дате импорта или сегодняшнему дню.
- Cancelled-only задачи не увеличивают покрытие принятых фактов.
- Элементы без timestamp не выглядят кликабельными и не ведут к началу записи.
- Инсайт открывает встречу внутри приложения, без полной перезагрузки страницы.

## 9. Подготовка и live facilitation

До записи создать planned update, parking topic и личный scratchpad. Во время записи включить standup mode, изменить таймбокс, вручную отметить пройденные апдейты, вопрос и тему для parking lot.

Критерий: таймбокс уведомляет, но не останавливает запись; нет автоматической оценки участников; заметки остаются локальными и отделены от transcript evidence; после перезапуска состояние восстановлено.

## 10. Безопасные имена спикеров

Проверить четыре типа реплик: самопредставление, явное представление другим человеком, обращение по имени и оскорбительное/нецензурное обращение.

- Безопасное имя показывается как кандидат с точным фрагментом доказательства.
- Составные имена с дефисом/апострофом отображаются корректно.
- Подтверждение требует выбора конкретного speaker cluster.
- Алиас не перезаписывает подтверждённое display name.
- Оскорбление, роль или обычное существительное не становятся именем.
- Отклонённая опасная строка не хранится открытым текстом, если достаточно salted fingerprint и причины.

## 11. Коллекции, поиск и RAG

1. Создать коллекцию из нескольких импортированных встреч.
2. Проверить полнотекстовый поиск, фильтры и переход к timestamp.
3. Дождаться локальной индексации и выполнить семантический запрос по одной встрече, коллекции и всему архиву.
4. Задать вопрос, ответа на который в выбранной области нет.

Критерий: ONNX-эмбеддинг строится без ошибки `token_type_ids`; ответы содержат реальные ссылки на фрагменты; при отсутствии доказательств система сообщает, что ответ не найден; scope не протекает в другие коллекции.

## 12. Миграция, приватность и восстановление после ошибок

- При наличии старых managed-настроек появляется неблокируемый случайным Escape/overlay диалог с явным выбором пользователя.
- До согласия настройки не меняются и данные не отправляются новому провайдеру.
- Повторное открытие после успешной миграции не показывает диалог снова.
- Отключение cloud/local-only режима действительно блокирует сетевую суммаризацию.
- Перезапуск во время индексации, импорта и генерации не портит встречу и даёт понятный путь повторить операцию.

## 13. Eval корпуса (разработческий тест)

Этот раздел выполняется локально и не требует публикации корпуса.

1. Зафиксировать leakage-safe набор по сериям встреч: одна серия не должна одновременно учить правила и оценивать их.
2. Запустить локальный Qwen corpus run на неизменном наборе.
3. Проверить resume/overwrite policy, явные статусы declined/failed и provenance языка/модели.
4. Сравнивать только агрегаты и обезличенные категории ошибок.
5. Запускать DeepSeek на том же наборе только при credentials и отдельном согласии на отправку расшифровок.

Release-решение нельзя принимать, пока нет независимых полных pure-status записей и ручной проверки доказательств. Красивый markdown без правильных фактов не считается улучшением.

## Рекомендуемый порядок одного тестового дня

1. Smoke build, запись и обычное саммари.
2. Автоопределение и короткий импорт с отменой/resume.
3. Один чистый стендап целиком: suggestion -> summary -> review -> series.
4. Один стендап с deep dive и один контрастный проектный митинг.
5. Имена, privacy-негативные сценарии и content window.
6. Коллекции/RAG и перезапуск приложения.
7. Только после UX-проверки - corpus eval.

## Что пока остаётся после этой ветки

По исходному Feature Catalog наиболее ценные следующие шаги после стабилизации этой сборки:

1. release-quality точность и скорость саммари на независимом корпусе;
2. пользовательский словарь и обучение на подтверждённых исправлениях имён/терминов;
3. meeting-type templates для планёрок, 1:1, интервью и клиентских звонков;
4. стабильные claim-level citations во всех типах саммари;
5. календарный контекст и только подтверждаемые outbound-действия;
6. AEC и speaker-count hint как отдельные улучшения качества capture/diarization.

Follow-up drafts, task push и live catch-up следует делать после доказанной точности review/series-потока. Conversation analytics и employee scoring не являются приоритетом для privacy-first продукта.
